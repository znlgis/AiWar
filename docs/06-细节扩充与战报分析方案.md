# 06 · 细节扩充、战报分析、地图真实化方案

> 状态：**待确认**。本文只做分析与设计，未改动任何游戏代码。
> 依据：现仓库代码实测（2026-11-15）、`docs/research/` 五份战役档案、`jiangshan-map` 仓库调研报告（HEAD `3d718671`）。

## 0. 现状盘点

先把现在的量级摆出来，后面的"加细节"才有参照。

| 战役 | 引擎 | 城邑 | 道路 | 部队 | 决策节点 | 专属语料 | 结局数 |
|---|---|---|---|---|---|---|---|
| 围魏救赵 | legacy | 16 | 30 | 5 | 7 | 约 240 条（`guiling-353bc/`） | 10 |
| 赤壁之战 | ops | 13 | 15 | 8 | 7 | **0** | 5 |
| 淝水之战 | ops | 18 | 20 | 10 | 8 | **0** | 5 |
| 四渡赤水 | ops | 20 | 29 | 13 | 8 | **0** | 5 |
| 淮海战役 | ops | 17 | 21 | 12 | 8 | **0** | 5 |

三个直接观察：

1. **四场 ops 战役共用一个 40 来条的通用语料池**（`packages/content/src/ops/narrator.ts` 的 `BASE`），"鼓角相闻""旗号未明"这类中性句在长江、淝水、赤水河、徐州重复出现。`MODERN_CORPUS`（现代军语版）定义了但**从未被引用**——淮海、四渡赤水的战报读起来仍是古代口吻。
2. **研究档案里的东西大半没进游戏**。`docs/research/` 合计 1500 余行，含 20 节点地图表、8 个决策点的完整台词、5 个特色机制、10 种结局分支；落进 `data.ts` 的只有约三分之一。
3. **结算页只有"分数"，没有"战报"**。`ResultView.vue` 渲染评级、分项得分、4 条亮点、最后 10 行日志。`state.battles` 里的逐日战斗记录在战斗结束时被删掉，玩家永远看不到打过哪几仗、折损多少。

## 1. 需求一：给五个战役加细节

### 1.1 缺口在哪

把"细节"拆成五层，逐层对照现状：

| 层 | 现状 | 缺口 |
|---|---|---|
| 地图要素 | 只有城邑点和道路线 | 没有山系、河流走向、关隘、渡口、海岸、湖泊 |
| 部队 | 8–13 支，只有兵力/士气/疲劳/训练四个数 | 没有将领属性、兵种编成、部队特性（如"久战""新募""不能夜战"） |
| 决策 | 7–8 个节点，每节点 3–4 选项 | 部分选项**只发一条战报，没有任何实际效果**（淝水 d7、赤壁 d7 都只有 `addReport`） |
| 过程事件 | 通用语料池 | 每战役专属的事件源几乎为零：疾疫、朱序传信、船工、民工、严寒 |
| 战报语料 | 4 场共用 40 余条 | 每场应 150 条以上专属语料 |

### 1.2 补法

**地图要素**：在 `OpsCampaign` 新增可选字段 `terrain: { kind: 'ridge'|'river'|'coast'|'lake'|'pass'; name?: string; points: [number,number][] }[]`。纯渲染用，不进推演，改起来不影响平衡回归。每场补 10–18 条，取自档案的"战场地理"章节（档案里河名、山名都是现成的）。

**部队**：`OpsArmyDef` 已有 `type/stealth/naval`，建议新增 `traits?: string[]`（如 `['newly_raised']`、`['veteran']`、`['no_night']`），在 `armyPower()` 里作为乘数参与，重量级不超过 ±12%。同时把每场部队从 8–13 支补到 14–18 支（档案里"双方兵力与编制"章节给出了完整序列）。

**决策**：每场从 7–8 个补到 10–12 个，并做两件事：
- 给现有"空选项"补实际效果（改动 `flags`/`vars`，让 AI 或战斗公式能读到）；
- 新增节点带**延迟后效**：选项改了 `vars`，3–8 天后由 `onTick` 触发事件。这条是本作最缺的"决策有回响"。

**过程事件**：在每场 `rules.ts` 的 `onTick` 里加 3–5 个条件事件，均有战报、有数值后果。示例：赤壁的"军中疾疫"（每 4 天曹军减员 + 士气下降，可选是否火攻速决）、淝水的"朱序传信"（情报可信度一次性提高）、四渡赤水的"追兵距离"、淮海的"民工疲劳"。

**语料**：每场新建 `packages/content/src/ops/<战役>/corpus.ts`，导出 150–200 条专属语料，通过 `makeOpsNarrator(corpus)` 注入。四场按年代分两类：赤壁、淝水用文言中性句；四渡、淮海用 `MODERN_CORPUS` 的路子，把"枪炮声""番号不详"这类现代词接上（这个坑已经在 `narrator.ts` 的注释里点明）。

### 1.3 每场要补的清单

| 战役 | 城池 | 道路 | 部队 | 决策 | 语料 | 新机制 |
|---|---|---|---|---|---|---|
| 围魏救赵 | 16→18 | 30→34 | 5→6 | 7→9 | 已足，补 20 条战后 | 无（引擎已定，仅维护） |
| 赤壁 | 13→24 | 15→40 | 8→14 | 7→10 | 0→160 | 疾疫、连环船、风向窗口 |
| 淝水 | 18→26 | 20→48 | 10→15 | 8→11 | 0→170 | 朱序情报、秦军自乱阈值、洛涧先胜 |
| 四渡赤水 | 20→26 | 29→52 | 13→16 | 8→11 | 0→180 | 佯动欺骗、渡口船数上限、扎西整编 |
| 淮海 | 17→26 | 21→50 | 12→16 | 8→12 | 0→190 | 三线配平（吃/挟/看）、支前运力、策反点数 |

后四行的机制直接来自 `docs/research/*` 的"特色机制"章节，已有完整设计说明，不需要重新想。

### 1.4 验收

- `pnpm test` 全绿，特别是 `regression.test.ts`：五场史实路线评级不得下降（赤壁 A、淝水 A、四渡 A、淮海 B、围魏救赵 A/S）。
- 每场战役可用的决策节点数 ≥ 10，且每个选项至少改一项 `flags/vars`（用一条测试卡住，防止再写"空选项"）。
- 每场战役语料 key 覆盖率 ≥ 80%：跑一遍完整对局，统计实际发出的 `kind` 有多少落在专属语料里。

## 2. 需求二：战役结束生成战报与战役分析

### 2.1 现在的结算页缺什么

`ResultView.vue` 现在给的是：评级印章、总分、6–8 条分项（带进度条）、4 条亮点、末 10 行日志、一句史实对照。

缺三样东西：

1. **过程**。从头到尾发生了什么——哪天打到哪、哪座城什么时候丢的、开局那个决策在多少天后反噬了。
2. **因果**。分项分数是结果，不是原因。"火攻破敌 30/30"背后是"你等了 6 天风，曹军这 6 天里减员 4000"。
3. **失败的复盘**。现在输掉的局，结算页与赢的局结构相同，只有结局文案不同。`docs/research/siduchishui.md:453` 明确写了"失败结局也要给出'如果当时……'的一句提示"，这条没实现。

### 2.2 数据缺口（这是必须先改内核的原因）

| 需要的数据 | 现状 |
|---|---|
| 每场战斗的双方兵力、逐日折损、胜负 | `state.battles` 在 `resolveBattle()` 末尾被 `filter` 删除，**战后即失** |
| 每座城易手的时间 | 只有 `state.citiesTaken: string[]`，无时间、无原属 |
| 每个节点选了哪一项 | 只有一行 `state.log` 文本，无 `nodeId → optionId` 结构 |
| 军令违令/失效次数 | `state.orders` 到期即删，无历史 |
| 情报命中率（发给玩家的兵力带 vs 真实兵力） | `state.traces` 只保留 8 天 |

所以这一步要动 `packages/sim/src/opsTypes.ts` 的 `OpsState`，新增四个只增不删的账本：

```ts
battleLog: { id, place, tick, days, atkLost, defLost, winner, ambush }[]
cityLog:   { city, tick, from, to, cause: 'assault'|'siege'|'empty' }[]
choiceLog: { nodeId, optionId, tick, title, label }[]
orderLog:  { tick, task, armyIds, target, result: 'ok'|'blocked'|'void' }[]
```

这四处都是 `push`，不参与任何判定，所以**不改变推演结果**，回归测试的 seed→结局映射保持不变。存档版本从 `v2` 升到 `v3`，旧存档读进来时给这四个字段补空数组即可（`save.ts` 加一个迁移函数）。

### 2.3 新增 `packages/sim/src/debrief.ts`

纯函数 `buildDebrief(state, campaign, score, packs)` → `Debrief`，零 DOM 依赖，可单测、可无头跑。

```ts
interface Debrief {
  verdict: 'win' | 'lose' | 'draw' | 'abandoned'
  headline: string            // 一句话战果，按战役模板生成
  chronicle: { tick, kind, text }[]   // 编年：决策/战斗/易城/断粮/天气，去噪后全量
  battles: { place, days, ours, theirs, result }[]
  cities: { name, tick, from, to }[]
  decisions: { tick, title, label, recommended, revertedAt?: number }[]  // revertedAt = 该决策在几天后反噬
  metrics: { key, label, value, hint }[]  // 双方折损、城邑得失、平均粮日、情报命中率、违令次数
  reading: { label, text }[]   // 分项解读：把 score.parts 每一项翻成一句人话
  turningPoint: { tick, text } // 关键转折：单条，按战役规则给出
  historyCompare: { same: string[], diff: string[] }  // 与史实主线对照
  hintIfLose: string           // 失败时的"如果当时……"
}
```

`turningPoint` 与 `historyCompare` 由每场 `rules.ts` 新增可选钩子 `debrief(state, campaign)` 提供初版，`debrief.ts` 做兜底——否则五场战役全得硬编码在通用代码里。

### 2.4 「不论输赢」怎么落实

三处要改：

1. **败局**：五个 `checkEnd` 里的失败分支（`rout`/`wiped`/`encircled`/`heavy`/`stall`）已经都会置 `over=true`，走的是同一个 `finish()`，所以败局本来就会进结算页。要补的是 `verdict` 判定与 `hintIfLose`。
2. **放弃**（现在完全没有战报）：`store/game.ts` 的 `abandon()` 目前直接删档回标题。改成先 `buildDebrief` 生成"残局战报"（标记 `verdict: 'abandoned'`），进结算页，页面底部提供"放弃并返回标题"。这是"不论输赢"最容易被忽略的一格。
3. **超时/未达成**：`endingId === 'stalemate'/'timeout'/'stall'` 归为 `draw`，一样出战报。

### 2.5 页面结构

`ResultView.vue` 从单栏改成两段：

- **上：战报**（可滚动）。标题 + 判词 + 编年表。编年表按"日"分组，每行左侧日期、右侧事件，战斗行加粗并附折损分档。整页可一键"复制文本"（不落文件，避免触平台 UGC 规则）。
- **下：战役分析**。四块——分项解读、关键转折、史实对照（同/异两列）、若败则"如果当时……"。

移动端编年表折叠成"只看决策与战斗"两档筛选。

### 2.6 验收

- 新增 `packages/sim/test/debrief.test.ts`：五场战役各跑胜局、败局、放弃三条路径，断言 `chronicle.length > 8`、`reading.length === score.parts.length`、`verdict` 正确。
- 回归测试的评级与分数**不得变化**（证明账本只读不写）。
- 存档迁移：v2 老档能读进 v3，四个账本为空时不报错。

## 3. 需求三：让地图更真实

### 3.1 jiangshan-map 调研结论

项目是"中国历史地图时间轴"静态站点，18 个朝代、204 个疆域快照。技术栈是**原生 JS + SVG + 自写 Web Mercator**，跟本作（Vue + SVG）同构，这点比想象中契合。

**能借的**（算法与字段设计，不是文件）：

| 项 | 具体 | 成本 |
|---|---|---|
| 折线圆角化 | 每条边两端缩进 `t = min(0.28, 4.2/len)`，拐点用二次贝塞尔过原顶点，边长 <1.6px 退回直边（`app.js:146-207`） | 低，半天 |
| 环方向修正 | shoelace 有向面积定正负，外环与洞反向，SVG 填充才能正确镂空 | 低，两小时 |
| Web Mercator 投影 | `west 66 / east 142 / south 14 / north 55` 映射到画布，1000×700 下约 13.16 px/度 | 低 |
| 地形晕渲公式 | Terrarium 解码 `R*256+G+B/256-32768` → 梯度 → 坡度/坡向 → 纸色系双色映射 | 中，需要 DEM |
| 标签避让打分 | 贪心放置 + 位移惩罚，比现在 `MapStage.vue` 里的矩形重叠剔除更稳 | 低，半天 |

**不能借的**（许可证，这条必须先说清）：

仓库 `LICENSE` 是 **GPL-3.0**。README 里另有分层说明：政权轮廓、一级政区、城邑/事件数据、地形晕渲图片都按 GPL-3.0；州郡府边界来自 CHGIS + Hartwell，**仅学术非商业、禁止再分发**。

结论：**一个字节的文件都不复制**。地名与经纬度是事实，但整表照抄有汇编权与 GPL 双重风险，得不偿失——本作只有 5 个战区，手录 100 来个点的成本远低于法律风险。存疑的"行政区划恢复度"也本就不该用（合规文档 §3.1 明令不画现代行政区划）。

### 3.2 三层改造（可独立开关，任一层不做都不影响其他层）

**L1 · 几何层（最见效，建议必做）**

现状最"假"的地方不是没有地形，是**势力范围**：`project.ts` 的 `makeAreas()` 拿占领城市的点做凸包，再按中心外扩 1.16 倍。凸包会把一片凹进去的敌占区吞成己方，五个势力叠成几块大三角。

改成**加权 Voronoi**：以所有已知城邑为种子点做泰森多边形，按归属着色，同势力相邻格子合并外轮廓；再用 3.1 的圆角算法柔化边界，让边线像手绘而不是多边形。城邑的"影响半径"可按 `kind`（都城 > 城池 > 关隘渡口）加权，都城辖域自然更大。

这条改完，同一份数据观感会立刻不同，且不动任何推演逻辑。

**L2 · 地形层**

新增 `terrain` 要素（见 §1.2）。渲染顺序：占位纸底色 → 山系（短笔触"山"字形，古地图笔法）→ 河流（圆角折线 + 名称）→ 湖泊/海岸（闭合面，浅色）→ 势力区半透明填充 → 道路 → 城邑 → 部队。

DEM 晕渲**不在第一批做**：它要新增位图资产（约 200–400 KB），且会与"极简水墨"的美术方向拉扯。建议做成一个默认关闭的图层开关，先验证观感再决定是否默认开。

**L3 · 制图层**

投影工具（Mercator，按战役经纬度区间自动算视野）、线宽分级（`vector-effect: non-scaling-stroke`）、标签避让打分、打印级纸面色。这一层纯 UI，独立交付。

### 3.3 坐标怎么来

五个战区的经纬度区间都不大：

| 战役 | 经度 | 纬度 | 城邑数 |
|---|---|---|---|
| 围魏救赵 | 114–120°E | 34–37°N | 18 |
| 赤壁 | 111–115°E | 28–32°N | 24 |
| 淝水 | 112–120°E | 30–34°N | 26 |
| 四渡赤水 | 103–108°E | 25–30°N | 26 |
| 淮海 | 115–119°E | 33–35°N | 26 |

做法：每个城邑按史书上可考的今地名查公开经纬度（公共事实），写进 `data.ts` 的新字段 `geo?: [lon, lat]`，离线跑一次脚本转为画布 `x/y`。**不改 `x/y` 字段本身**，老存档、老测试完全不受影响；`geo` 只用于新渲染路径与"真实比例校验"（比如检查"临淄—大梁 3 日"与两城实际距离是否匹配，不匹配就调 `days`）。

这条顺带解决一个隐性问题：现有部分城邑坐标明显不成比例（四渡赤水把皎平渡画到昆明以南，`MapStage.vue` 的注释里就记着这桩旧账）。

### 3.4 合规红线（不改）

- 仍是示意古地图：不画现代行政区划、国界线、现行省界。
- 城邑不标今地名；今地名只出现在史实页文字里，并注明"示意"。
- 不使用任何第三方图片资产；山形、河线、城郭全部自绘 SVG。
- 不引入第三方地图库（`docs/02` 的技术栈约定仍是"运行时只有 Vue"）。

### 3.5 体积与验收

- 预算：纯矢量方案下整包增幅 < 120 KB（当前约 95 KB，预计 200 KB 上下）。若开 DEM 图层再加 200–400 KB，仍远低于 3 MB 预算与 50 MB 上限。
- 验收：五个战役各截一张全图，与现状对比；600×800 竖屏下城名不重叠、势力边界不互相穿透；`pnpm toy:check` 0 error。

## 4. 分批与工作量

按"能独立验收"切四批，每批结束给可运行构建 + 对比截图。

| 批次 | 内容 | 主要文件 | 预计 |
|---|---|---|---|
| **B1** | 需求二全部：内核埋点、`debrief.ts`、结算页改版、放弃路径出战报 | `opsTypes.ts`、`opsEngine.ts`、`save.ts`、`debrief.ts`(新)、`ResultView.vue`、`game.ts` | 1 个工作段 |
| **B2** | 需求一：四场 ops 战役的城/路/部队/决策/语料/机制扩充 | `ops/*/data.ts`、`ops/*/rules.ts`、`ops/*/corpus.ts`(新)、`packs.ts` | 2–3 个工作段 |
| **B3** | 需求三 L1+L3：Voronoi 势力区、圆角化、投影工具、标签避让 | `project.ts`、`MapStage.vue`、`map/voronoi.ts`(新)、`map/geo.ts`(新) | 1–2 个工作段 |
| **B4** | 需求三 L2 + 需求一收尾：地形要素与山河水系、围魏救赵补节点、全量回归 | `ops/*/data.ts`、`map/TerrainLayer.vue`(新)、文档 | 1 个工作段 |

顺序建议：**B1 → B3 → B2 → B4**。理由：B1 是纯增量（不改推演结果），风险最低；B3 只动渲染层，也是纯增量；B2 会动平衡，必须放在有测试基线之后；B4 收尾。

改动面最大的风险在 B2：五场战役的数值一改，`regression.test.ts` 的"史实路线必须达 A/B"和"史实难度不低于地狱"两把锁会立刻报警。应对是先只加不删（新城邑、新部队、新节点），跑一遍看哪场的守不住，再有针对性地调，不预先改断言。

## 5. 需要你确认的六件事

1. **范围**：三项全做（B1–B4），还是先做 B1+B3？后两者加起来约 2–4 个工作段，能最快看到"战报有了、地图像了"。
2. **地图风格**：势力区用 Voronoi 精确区划（边界清晰、像地图集），还是保留现在的大块晕染（更像水墨）？我倾向前者，但这是审美选择。
3. **DEM 地形晕渲**：要不要？（默认关闭的图层开关，还是干脆不做）
4. **战报形态**：只做站内页面，还是要"复制文本"/"生成结果卡"？后者涉及剪贴板与 canvas 导出，平台规则上要试探。
5. **细节扩充的量级**：按 §1.3 的表（城 +6~13、决策 +2~4、语料 +160~190），还是更小（只补语料和新机制，不动地图数据）？
6. **围魏救赵要不要重做**：它现在跑 legacy 引擎，与另外四场不是一套代码。给它补细节意味着要么迁移到 ops 引擎（工作量大、回归风险高），要么只在 legacy 上加节点与语料（保守）。我建议后者。
